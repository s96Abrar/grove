# Building and releasing Grove

## Release policy

Releases are **tagged only**, as requested. There is no cron/scheduled release, daily build or automatic version bump. Normal CI checks run on main pushes, pull requests or an explicit manual run. The separate release workflow runs only on a pushed `vMAJOR.MINOR.PATCH` tag and rejects a version mismatch or dirty checkout.

This repository is local. No remote, hosted CI run, signing credential, uploaded artifact or published release was created. Workflow files are prepared for a future GitHub remote. Local commands work now without one.

`release.json` is the single version/build/bundle-identifier/minimum-OS source. Keep the build number increasing when preparing a release. Current own-source license is MIT; dependency notices are embedded in the app. No account, activation or telemetry service is part of release or runtime behavior.

## Local development and delivery

```sh
make build
make check
make package
```

`make build` creates `dist/Grove.app` for the host architecture with a hardened-runtime ad-hoc signature. The original icon is `Resources/AppIcon.png`; editable vector drawing source is `scripts/render-icon.swift`, regenerated by `make icon`. All standard macOS icon sizes are packaged into AppIcon.icns.

`make check` runs real temporary Git checks, workspace corruption/recovery checks, release-policy checks, the PTY/screen backend check, package validation and the actual app termination/relaunch harness. The GUI harness uses a temporary workspace and terminates only its own app instances/screen session. It needs a logged-in macOS graphical session; CI must fail rather than silently skip it when configured.

`make package` produces a **local-only** ZIP, SHA256SUMS and source/build manifest under `dist/releases/<version>-local/`. Files include `-local` and the manifest says `local-adhoc`. A local archive is not a notarized public release. Existing release folders are never silently replaced; archive a previous local output elsewhere or remove only the generated folder intentionally before rebuilding the same version.

To build both architectures locally:

```sh
GROVE_ARCHS="arm64 x86_64" python3 scripts/release.py --mode local
```

The executable is merged with lipo, actual slices are verified, and the ZIP is extracted into a fresh directory and revalidated. Cross-compiling an Intel slice on Apple Silicon does not establish Intel runtime behavior; the prepared CI matrix runs on both native architectures.

## Public release prerequisites

The current Mac has **no valid code-signing identity**. Nothing has been notarized or submitted to Apple. These prerequisites are required before a public release:

1. A future GitHub repository and protected release tags. Keep the current local history and add a remote only when you choose to.
2. Developer ID Application certificate/private key for the chosen bundle identity; use its SHA-1 fingerprint, not a nonunique display name.
3. Apple notarization credentials, either an existing local notarytool keychain profile or App Store Connect API credentials with suitable permissions.
4. A `release` GitHub Environment with protected access and the secrets listed below. Configure reviewers if publishing should need an additional human approval.
5. Successful native CI/GUI checks and validation on the supported macOS versions. Current local tests establish the current Apple Silicon/macOS host, not every supported OS/hardware combination.

The pipeline signs with hardened runtime and a secure timestamp, submits to Apple, requires `Accepted`, staples and validates the ticket, runs Gatekeeper assessment, then rebuilds and round-trips the final delivery archive. It stops on missing credentials, unsigned/ad-hoc signatures in production mode, incomplete universal binaries, version/tag mismatch, dirty source, rejected notarization, missing stapling or failed validation. It never falls back from production signing to ad-hoc signing.

## Prepared GitHub workflows

- `.github/workflows/ci.yml`: Apple Silicon and Intel macOS 26 runners, explicitly selected Xcode 26.6, real checks and local-only developer artifacts retained for 14 days.
- `.github/workflows/release.yml`: tag push → reusable native quality matrix → isolated signing job → universal app → Apple notarization/stapling → Gatekeeper + ZIP validation → GitHub Release with ZIP, checksums and manifest.

Official actions are pinned to full commit IDs and checkout credential persistence is disabled. Pull request jobs have read-only content permissions and no signing secrets. Only the final release job gets content-write permission. The credential helper creates a dedicated temporary keychain and does not change the login/default keychain or developer portal state. Cleanup runs even after a failed signing step. No private key is packaged in artifacts.

Future `release` environment secrets:

| Secret | Meaning |
|---|---|
| `APPLE_CERTIFICATE_P12_BASE64` | Base64-encoded exported Developer ID Application certificate and private key. |
| `APPLE_CERTIFICATE_PASSWORD` | Password protecting that export. |
| `APPLE_CERTIFICATE_SHA1` | Exact SHA-1 of the signing certificate. |
| `APPLE_API_KEY_P8` | App Store Connect API private-key content. |
| `APPLE_API_KEY_ID` | API key identifier. |
| `APPLE_API_ISSUER_ID` | API issuer identifier. |

Do not put these values in Git, issue bodies or logs. No setup step asks for secrets in chat. The helper operates only inside an isolated CI runner. For a local signed release, use an existing keychain identity and profile:

```sh
export GROVE_SIGNING_IDENTITY="<40-character certificate SHA-1>"
export GROVE_NOTARY_PROFILE="<existing notarytool profile>"
python3 scripts/release.py --mode production --tag v0.3.0 --preflight-only
python3 scripts/release.py --mode production --tag v0.3.0
```

The tag must exist locally at HEAD and match release.json. Credentials are not created or changed by these commands. After the future remote/environment is configured and the release has been reviewed:

```sh
git tag -a v0.3.0 -m "Grove 0.3.0"
git push origin v0.3.0
```

These are future operator instructions, not actions already taken. Tag push will trigger publication once all configured gates pass. Re-runs do not overwrite an already published release. Fix a failed release before tagging a new version; do not move a published tag.

## Evidence and current limits

Local validation is recorded in VALIDATION.md. The workflow YAML and command scripts can be checked locally, but no hosted workflow run has occurred without a remote. Signing/notarization is implemented and fail-closed, but cannot be called end-to-end verified without credentials. Minimum macOS 14 compatibility and Intel runtime behavior remain explicit test requirements. The system screen backend has terminal-protocol limits compared with modern multiplexers; authenticated coding-agent scenarios still need their own acceptance runs. Full Supacode feature parity and automatic updates remain separate from packaging readiness.

References: [Apple notarization](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution), [Apple distribution validation](https://help.apple.com/xcode/mac/current/en.lproj/dev033e997ca.html), [GitHub workflow triggers](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax), [Apple Silicon runner inventory](https://github.com/actions/runner-images/blob/main/images/macos/macos-26-arm64-Readme.md), [Intel runner inventory](https://github.com/actions/runner-images/blob/main/images/macos/macos-26-Readme.md).

### Cross-compilation toolchain note

The build explicitly selects SwiftPM’s native engine and an architecture/minimum-OS target triple. On the current Swift 6.4 host, the default swiftbuild engine compiled a build-time dependency helper for the destination CPU, which could not execute without Rosetta. The native engine keeps that helper host-native. Swift 6.4 marks this engine deprecated; CI is pinned to the documented Xcode 26.6 toolchain. Revalidate this path before upgrading toolchains or removing the fallback. No Rosetta installation or permission bypass is performed.
